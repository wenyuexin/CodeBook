# Java并发

## 一、线程基础

### 1\. 创建线程有哪几种方式？

- **继承** `Thread` 类：重写 `run()` 方法。\
  优点：简单；缺点：单继承限制。

- **实现** `Runnable` 接口：实现 `run()` 方法。\
  优点：可继续实现其他接口或继承类；缺点：无返回值。

- **实现** `Callable` 接口：实现 `call()` 方法，配合 `FutureTask` 使用。\
  优点：有返回值、可抛出异常；缺点：需要额外包装。

- **使用线程池**（`ExecutorService`）：\
  优点：降低资源消耗，提高线程管理能力；缺点：需要合理配置参数。

### 2\. `Runnable` 和 `Callable` 的区别？

|对比项|Runnable|Callable|
|-|-|-|
|方法|`run()`|`call()`|
|返回值|void|V（泛型）|
|异常|不能抛出 checked 异常|可以抛出异常|
|使用方式|`new Thread(runnable)`|`FutureTask` + `Thread` 或线程池|

## 二、可见性与有序性：`volatile`

### 3\. `volatile` 的作用是什么？能保证原子性吗？

**作用**：

- **保证可见性**：一个线程修改后，其他线程立即可见。

- **禁止指令重排序**：通过内存屏障实现。

**不能保证原子性**：例如 `volatile int count; count++` 不是原子操作。

**适用场景**：

- 布尔状态标志（`volatile boolean flag`）

- 双重检查锁（DCL）中的单例对象

- 读多写少且写操作不依赖当前值的场景

**底层原理**：在 x86 处理器下生成 `lock` 前缀指令，触发缓存一致性协议（如 MESI），使其他 CPU 的缓存行失效。

## 三、内置锁：`synchronized`

### 4\. `synchronized` 的三种使用方式及锁对象？

- **实例方法**：锁是当前实例对象（`this`）。

- **静态方法**：锁是当前类的 `Class` 对象。

- **同步代码块**：锁是括号内指定的任意对象。

### 5\. `synchronized` 的可重入性是如何实现的？

每个锁关联一个**计数器**和**所有者线程**。线程再次进入已持有的锁时，计数器 +1；退出时计数器 -1，归零时释放锁。\
JVM 层面通过 `monitorenter` / `monitorexit` 指令实现，每个对象有一个 monitor，monitor 内部维护计数器。

### 6\. JDK 6 之后 `synchronized` 做了哪些优化？

- **锁升级**：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。

- **偏向锁**：无竞争时消除同步（CAS 操作）。

- **轻量级锁**：通过 CAS 自旋，避免内核态切换。

- **适应性自旋**：自旋时间根据前一次自旋结果动态调整。

- **锁粗化**：将多个连续的加锁/解锁操作合并。

- **锁消除**：通过逃逸分析去掉不可能竞争的锁。

### 7\. `synchronized` 和 `ReentrantLock` 的区别？

|对比项|synchronized|ReentrantLock|
|-|-|-|
|实现层级|JVM 关键字（内置锁）|Java API 类|
|锁释放|自动（异常/代码块结束）|必须在 `finally` 中手动 `unlock()`|
|可中断|不支持|支持 `lockInterruptibly()`|
|超时获取|不支持|支持 `tryLock(timeout, unit)`|
|公平锁|非公平|可构造公平锁（`new ReentrantLock(true)`）|
|条件变量|每个锁只有一个 `wait/notify`|多个 `Condition`|
|性能|JDK6 后已优化，简单场景相当|高竞争下略优|

## 四、线程池（`ThreadPoolExecutor`）

### 8\. `ThreadPoolExecutor` 的核心参数及作用？

|参数|作用|
|-|-|
|`corePoolSize`|核心线程数，即使空闲也会存活（除非设置 `allowCoreThreadTimeOut`）|
|`maximumPoolSize`|最大线程数|
|`keepAliveTime`|非核心线程空闲存活时间|
|`unit`|时间单位|
|`workQueue`|任务阻塞队列（如 `ArrayBlockingQueue`, `LinkedBlockingQueue`, `SynchronousQueue`）|
|`threadFactory`|创建线程的工厂，可自定义线程名、优先级等|
|`handler`|拒绝策略（当队列和线程池都满时）|

### 9\. 线程池的任务提交流程（执行顺序）？

1. 当前线程数 < `corePoolSize` → 创建新线程执行任务。

2. 当前线程数 ≥ `corePoolSize` → 任务放入 `workQueue`。

3. 队列已满且线程数 < `maximumPoolSize` → 创建非核心线程执行任务。

4. 队列已满且线程数 = `maximumPoolSize` → 执行拒绝策略。

### 10\. `Executors` 工厂方法创建的几种线程池有何问题？为什么不推荐？

|方法|问题|
|-|-|
|`newFixedThreadPool`|核心=最大，无界队列（`LinkedBlockingQueue`），可能导致 OOM|
|`newCachedThreadPool`|核心=0，最大=Integer.MAX_VALUE，同步队列，可能导致线程数过多|
|`newSingleThreadExecutor`|单线程，无界队列|
|`newScheduledThreadPool`|支持定时/延迟任务，但同样存在无界队列风险|

**不推荐原因**：无界队列或无限线程数容易引发资源耗尽（OOM 或线程爆炸）。**建议手动创建** `ThreadPoolExecutor`。

### 11\. 线程池的拒绝策略有哪些？适用场景？

|策略|行为|适用场景|
|-|-|-|
|`AbortPolicy`（默认）|抛出 `RejectedExecutionException`|关键任务，必须明确处理|
|`DiscardPolicy`|静默丢弃|可丢失的非关键任务|
|`DiscardOldestPolicy`|丢弃队列头部（最旧）任务，重试提交|追求新任务优先|
|`CallerRunsPolicy`|由调用者线程执行|降级，减缓任务提交速度|

### 12\. 如何扩展 `ThreadPoolExecutor`？典型用途？

重写 `beforeExecute(Thread, Runnable)`、`afterExecute(Runnable, Throwable)`、`terminated()`。\
用途：

- 记录任务执行时间

- 打印日志、监控指标

- 清理 ThreadLocal

- 任务执行异常统一处理

## 五、并发集合与同步工具

### 13\. `ConcurrentHashMap` 的实现原理？

- **JDK 1.7**：分段锁（`Segment` 数组），每个 Segment 独立 `ReentrantLock`，默认 16 个并发级别。

- **JDK 1.8+**：`synchronized` + CAS。

  - 数组 + 链表/红黑树。

  - 写操作：对桶首节点加 `synchronized`，使用 CAS 进行扩容和数据迁移。

  - 读操作：无锁（`volatile` 保证可见性）。

- **优点**：高并发下吞吐量远高于 `Hashtable` 或 `Collections.synchronizedMap`。

### 14\. `CountDownLatch`、`CyclicBarrier`、`Semaphore` 的区别？

|工具|作用|可重用|典型场景|
|-|-|-|-|
|`CountDownLatch`|等待一组线程完成计数|否|主线程等待多个子任务完成|
|`CyclicBarrier`|多个线程互相等待到某个屏障点|是|多阶段计算、并行处理|
|`Semaphore`|控制同时访问资源的线程数|是|限流、连接池控制|

**补充**：

- `CountDownLatch` 计数不可重置；`CyclicBarrier` 可通过 `reset()` 重置。

- `Semaphore` 支持公平/非公平模式，可获取/释放多个许可。

## 六、锁机制深入

### 15\. 什么是乐观锁和悲观锁？Java 如何实现？

- **悲观锁**：假设冲突高，先加锁再操作。实现：`synchronized`、`ReentrantLock`、数据库行锁。

- **乐观锁**：假设冲突低，先操作，更新时检查版本。实现：CAS（`AtomicXXX` 类）、版本号机制（JPA 的 `@Version`）。

- **适用场景**：

  - 悲观锁：写多读少，冲突频繁。

  - 乐观锁：读多写少，冲突概率低。

### 16\. CAS 的原理、问题及解决方案？

**原理**：Compare And Swap，由 CPU 原子指令支持（如 x86 的 `cmpxchg`）。三个操作数：内存地址 V，期望值 A，新值 B。当 V == A 时更新为 B，否则重试。

**问题**：

1. **ABA 问题**：变量被 A→B→A，CAS 误认为未变化。

   - 解决：使用 `AtomicStampedReference` 或 `AtomicMarkableReference`（版本号/标记）。

2. **循环时间长开销大**：高竞争下自旋消耗 CPU。

   - 解决：限制自旋次数，或改用锁。

3. **只能保证一个共享变量的原子操作**。

   - 解决：使用 `AtomicReference` 封装多个变量，或使用锁。

## 七、`ThreadLocal`

### 17\. `ThreadLocal` 的实现原理？

每个 `Thread` 内部有一个 `ThreadLocalMap`，键为 `ThreadLocal` 实例（弱引用），值为存储的对象。

- `set(T value)`：获取当前线程的 map，若存在则设置，否则创建 map 并设置。

- `get()`：同理，若当前线程没有 map 或没有该 key，返回初始值（通过 `initialValue()`）。

- 每个线程独立存储，因此无需加锁。

### 18\. `ThreadLocal` 为什么会内存泄漏？如何避免？

**原因**：`ThreadLocalMap` 的 key 是弱引用，但 value 是强引用。当 `ThreadLocal` 对象被 GC 后，key 变为 `null`，但 value 仍然存在（被当前线程的 map 引用），导致无法回收。

**避免**：

- 使用完 `ThreadLocal` 后显式调用 `remove()` 方法。

- 尽量将 `ThreadLocal` 定义为 `static`（但 static 变量不会自动释放，仍需注意）。

- **最佳实践**：在 try-finally 块中调用 `remove()`，尤其在线程池中使用时。

## 八、`CompletableFuture`

### 19\. `CompletableFuture` 和 `Future` 的区别？

|对比项|Future|CompletableFuture|
|-|-|-|
|获取结果方式|`get()` 阻塞|回调、组合、异常处理|
|手动完成|不支持|`complete()`、`completeExceptionally()`|
|任务编排|无法链式组合|支持 `thenApply`、`thenCompose`、`thenCombine` 等|
|异常处理|只能通过 `get()` 捕获 `ExecutionException`|`exceptionally`、`handle` 直接处理|
|组合多个任务|`ExecutorService.invokeAll` 较笨拙|`allOf`、`anyOf`|

### 20\. 常见异步执行方式？

- `supplyAsync(Supplier<U> supplier)`：有返回值的异步任务。

- `runAsync(Runnable runnable)`：无返回值的异步任务。

- 可传入自定义 `Executor`，否则使用 `ForkJoinPool.commonPool()`。

### 21\. `thenApply`、`thenCompose` 和 `thenCombine` 的区别？

|方法|作用|输入|输出|类似 Stream 操作|
|-|-|-|-|-|
|`thenApply`|对上一个结果做同步转换|`T`|`U`|`map`|
|`thenCompose`|将上一个结果转为另一个 `CompletableFuture`（扁平化）|`T`|`CompletableFuture<U>`|`flatMap`|
|`thenCombine`|等待两个独立的 `CompletableFuture`，合并结果|`(T, U) -> V`|`CompletableFuture<V>`|类似 `zip`|

### 22\. 如何处理 `CompletableFuture` 中的异常？

- `exceptionally`：任务异常时返回默认值或执行备选逻辑。

- `handle`：无论正常还是异常都会执行，通过判断 `Throwable` 是否为 null 来处理。

- `whenComplete`：类似 `handle`，但不改变结果，仍会抛出异常。

### 23\. `allOf` 和 `anyOf` 的作用？

- `allOf`：等待所有任务完成，返回 `CompletableFuture<Void>`，需配合 `join()` 等待全部完成。

- `anyOf`：任意一个任务完成即结束，返回第一个完成的结果。

### 24\. 使用 `CompletableFuture` 时如何避免线程池耗尽？

默认使用 `ForkJoinPool.commonPool()`，该池大小 = CPU 核数 - 1。大量阻塞 I/O 任务会导致线程饥饿。

**解决方案**：

- 为 `CompletableFuture` 显式传递自定义线程池（如 `ExecutorService`）。

- 区分 CPU 密集型和 I/O 密集型任务，配置不同的线程池。

- 避免在 `thenApply` 等回调中做阻塞操作，可改用 `thenApplyAsync` 并传递专用线程池。

### 25\. 如何实现超时控制？（Java 9+）

- `orTimeout(long timeout, TimeUnit unit)`：超时后抛出 `TimeoutException`。

- `completeOnTimeout(T value, long timeout, TimeUnit unit)`：超时后返回默认值。

### 26\. 开放设计题：使用 `CompletableFuture` 并行调用多个外部 API 并聚合结果。

**思路**：

- 使用 `supplyAsync` 为每个 API 调用创建 `CompletableFuture`。

- 使用 `allOf` 等待所有 API 完成。

- 使用 `join()` 获取每个 API 的结果（或者 `thenApply` 收集到 List）。

- 聚合结果后返回。

- 设置超时和异常处理（`exceptionally` 提供降级值）。

```java
CompletableFuture<Result> api1 = CompletableFuture.supplyAsync(() -> callApi1());
CompletableFuture<Result> api2 = CompletableFuture.supplyAsync(() -> callApi2());
CompletableFuture.allOf(api1, api2).join();
Result combined = combine(api1.join(), api2.join());
```

## 九、补充：Java 内存模型（JMM）与 AQS

### 27\. 简述 Java 内存模型（JMM）及其解决的问题？

**定义**：JMM 定义了线程与主内存之间的抽象关系。

* 所有变量存于主内存。

* 每个线程有自己的工作内存（缓存、寄存器），线程对变量的操作必须在工作内存中进行，不能直接读写主内存。

**解决的问题**：

* **可见性**：通过 `volatile`、`synchronized`、`final` 保证。

* **原子性**：通过锁、CAS 保证。

* **有序性**：通过 `happens-before` 规则保证。

`happens-before` 规则：程序次序规则、volatile 规则、锁规则、传递性等。

### 28\. 什么是 AQS？如何支持 `ReentrantLock` 和 `CountDownLatch`？

**AQS**（AbstractQueuedSynchronizer）：JUC 包的基础框架，内部维护一个 `volatile int state` 和一个 FIFO 等待队列。

* `ReentrantLock`：

  * 公平/非公平策略，通过 `tryAcquire` / `tryRelease` 修改 state（0 表示未锁，≥1 表示重入次数）。

  * 获取锁失败则进入队列阻塞。

* `CountDownLatch`：

  * state 初始化为 N。

  * `countDown()` 使用 CAS 将 state-1，为 0 时唤醒所有等待线程。

  * `await()` 在 state != 0 时阻塞。
