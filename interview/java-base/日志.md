# 日志

## 1. 基础概念篇

### 问题 1：Java 中日志门面和日志实现分别是什么？为什么需要日志门面？

**参考答案**

- **日志门面**：提供一套统一的日志 API，不负责具体日志输出，例如 SLF4J、JCL。
- **日志实现**：真正实现日志输出、格式化、存储等功能的框架，例如 Log4j2、Logback、JUL。

**需要门面的原因**：

- 避免应用代码与具体日志实现强耦合，便于更换底层框架而不修改代码。
- 统一 API 降低学习成本，也方便第三方类库与你的项目使用同一套日志 API。
- 通过门面可以做到“编译期绑定”，性能好且无侵入。

---

### 问题 2：SLF4J 和 Log4j、Logback 之间的关系是什么？

**参考答案**

- SLF4J 是日志门面，Log4j 和 Logback 是日志实现。
- Logback 是 Log4j 的继任者，由同一作者开发，原生支持 SLF4J，无需适配层。
- 使用 SLF4J + Logback 时，只需引入 `slf4j-api` 和 `logback-classic`，后者已包含对 SLF4J 的实现。
- 若要使用 SLF4J + Log4j2，则需要额外引入 `log4j-slf4j-impl` 作为适配器。

---

### 问题 3：简述日志门面模式（外观模式）在日志框架中的应用。

**参考答案**

- 外观模式为子系统的一组接口提供一个统一的简化接口。
- 在日志体系中，SLF4J 就是外观，它隐藏了不同日志实现（Logback、Log4j2、JUL）的复杂性和差异。
- 应用程序只依赖 SLF4J API，不需要关心底层是同步还是异步、输出到文件还是控制台。
- 这样做降低了系统的耦合度，也提高了扩展性。

## 2. 框架对比篇

### 问题 4：Log4j 1.x、Log4j 2.x 和 Logback 之间有哪些主要区别？

**参考答案**

| 特性         | Log4j 1.x            | Logback      | Log4j 2.x                   |
| ---------- | -------------------- | ------------ | --------------------------- |
| 维护状态       | 已停止维护，有严重安全漏洞        | 活跃维护         | 活跃维护                        |
| 性能         | 较差（同步锁严重）            | 优秀           | 极高（基于 LMAX Disruptor 的无锁异步） |
| 配置格式       | XML / properties     | XML / Groovy | XML / JSON / YAML           |
| 对 SLF4J 支持 | 需要适配器（slf4j-log4j12） | 原生支持         | 需要适配器（log4j-slf4j-impl）     |
| 自动重载配置     | 不支持                  | 支持           | 支持                          |

**结论**：新项目应避免使用 Log4j 1.x，优先选择 Logback 或 Log4j 2.x。

---

### 问题 5：为什么说 Log4j 2 的异步日志性能极高？其实现原理是什么？

**参考答案**

- Log4j 2 采用 **LMAX Disruptor**（无锁环形缓冲区）实现异步日志。
- 业务线程只负责将日志事件放入 Disruptor 队列，立即返回；后台消费者线程批量处理。
- 相比传统的 `ArrayBlockingQueue`，Disruptor 使用内存屏障、预填充、避免伪共享等技术，大幅减少锁竞争和上下文切换。
- 测试数据显示，Log4j 2 异步日志的吞吐量可达 Logback 异步模式的数倍甚至十数倍。

## 3. 使用与配置篇

### 问题 6：如何配置 Logback 将不同级别的日志输出到不同文件？

**参考答案**在 `logback.xml` 中配置多个 `appender` 和 `filter`，例如：

```xml
<configuration>
    <appender name="FILE_INFO" class="ch.qos.logback.core.FileAppender">
        <file>logs/info.log</file>
        <filter class="ch.qos.logback.classic.filter.LevelFilter">
            <level>INFO</level>
            <onMatch>ACCEPT</onMatch>
            <onMismatch>DENY</onMismatch>
        </filter>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <appender name="FILE_ERROR" class="ch.qos.logback.core.FileAppender">
        <file>logs/error.log</file>
        <filter class="ch.qos.logback.classic.filter.LevelFilter">
            <level>ERROR</level>
            <onMatch>ACCEPT</onMatch>
            <onMismatch>DENY</onMismatch>
        </filter>
        <encoder>...</encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="FILE_INFO"/>
        <appender-ref ref="FILE_ERROR"/>
    </root>
</configuration>
```

也可以使用 `ThresholdFilter` 按级别范围过滤。

### 问题 7：什么是 MDC（Mapped Diagnostic Context）？它的典型使用场景是什么？

**参考答案**

- **MDC** 是 SLF4J 提供的功能，允许在日志输出中自动添加上下文信息（如用户 ID、请求 ID、Session ID）。
- 使用方式：`MDC.put("userId", "12345")`，在日志配置中使用 `%X{userId}` 输出。
- 典型场景：Web 应用中，在过滤器里将请求 ID 放入 MDC，之后整个请求链路的日志都能带上该 ID，便于追踪分布式调用。
- **注意**：使用完后应在 `finally` 块中调用 `MDC.clear()` 或 `MDC.remove()`，避免内存泄漏（尤其是在线程池环境中）。

## 4. 调优与排查篇

### 问题 8：线上日志量过大导致磁盘空间不足，你会如何优化？

**参考答案**

1. **调整日志级别**：将开发调试用的 `DEBUG` 级别在生产环境改为 `INFO` 或 `WARN`。
2. **配置滚动策略**：使用 `TimeBasedRollingPolicy`（按天/小时滚动）和 `SizeBasedTriggeringPolicy`（按文件大小滚动），并限制最大历史文件数或总大小。
3. **异步日志**：采用 Logback 的 `AsyncAppender` 或 Log4j 2 的异步 appender，减少业务线程阻塞，但需注意队列满时的丢弃策略。
4. **过滤无用日志**：对频繁打印但无价值的日志（如心跳日志）单独关闭或降级。
5. **日志采样**：对于极高频率的日志，可以按比例采样（如每 100 次打印一次）。
6. **集中日志收集**：将日志发送到 ELK 等系统，本地仅保留短期必要日志。

### 问题 9：在使用 SLF4J 时，`logger.debug("value:" + user.getName())` 这种写法有什么问题？应该如何改进？

**参考答案**

- 问题：即使当前日志级别高于 `DEBUG`，字符串拼接操作 `"value:" + user.getName()` 仍然会执行，造成不必要的性能开销（尤其是拼接复杂对象或循环中）。
- 改进方法：使用占位符方式，`logger.debug("value: {}", user.getName())`。
  - SLF4J 会先检查日志级别，若 `debug` 未启用，则不进行参数计算和字符串拼接。
- 更彻底的优化：对于代价极高的参数（如调用远程服务），可以显式判断 `if (logger.isDebugEnabled()) { ... }`。

### 问题 10：如何解决由于多个日志框架共存导致的“无日志输出”或“日志重复打印”问题？

**参考答案**

- 问题常见场景：项目中同时引入了 Logback、Log4j、JUL，且类路径下有多个 `slf4j` 绑定。
- **无日志输出**：通常是因为 SLF4J 找到了多个静态绑定（`StaticLoggerBinder`），会输出警告并随机选择一个，可能选到不正确的实现。
  - 解决：使用 `mvn dependency:tree` 排查并排除多余的日志实现依赖。
- **日志重复打印**：例如 Logback 和 `log4j-over-slf4j` 同时存在，导致一条日志被两个 appender 处理。
  - 解决：确保只保留一个实现，并正确使用桥接包（如 `jcl-over-slf4j`、`log4j-over-slf4j`）将旧 API 桥接到 SLF4J。
- 推荐做法：使用 `spring-boot-starter-logging`（默认 Logback）或 `spring-boot-starter-log4j2`，它已经处理好了依赖冲突。

## 5. 开放思考题

### 问题 11：你如何设计一个大型微服务系统的日志规范？（无标准答案，考察思路）

**参考答案要点**

- **统一门面**：强制使用 SLF4J API，禁止直接使用 Log4j 或 Logback 原生 API。
- **日志级别**：生产环境默认 INFO；DEBUG 只在需要排查问题时动态开启。
- **日志格式**：统一包含时间戳、线程名、级别、类名、请求追踪 ID（MDC）、消息体、异常堆栈。
- **追踪 ID**：在网关生成 TraceId，通过 RPC 透传，确保跨服务日志可关联。
- **滚动策略**：按天滚动，单文件最大 1GB，保留 30 天。
- **异步输出**：核心服务使用 Log4j 2 异步 appender，避免日志拖慢业务。
- **日志采集**：使用 Filebeat 或 Logstash 将日志发送到 Elasticsearch，构建日志中心。
- **敏感信息脱敏**：配置 Layout 或 Filter 对身份证、手机号等自动脱敏。
