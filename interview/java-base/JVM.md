# JVM 

## 1. 对象创建与类加载机制

### 1.1 一个对象从 new 到使用，经历了哪些步骤？

在 JVM 中，创建一个对象大致经历以下过程：

1. **类加载检查**：首先检查对应的类是否已经被加载、连接、初始化。如果没有，则先执行类加载过程。
2. **分配内存**：对象所需内存大小在类加载完成后可以完全确定，JVM 会在堆中划分一块内存给新对象。分配方式有“指针碰撞”（内存规整）和“空闲列表”（内存不规整），具体取决于垃圾收集器是否带有压缩整理功能。
3. **初始化零值**：分配的内存空间会被初始化为零值（不包括对象头），保证了对象的实例字段可以不赋初值直接使用。
4. **设置对象头**：填充对象头信息，如哈希码、GC 分代年龄、类型指针等。
5. **执行 `<init>` 方法**：调用构造方法，对实例变量进行初始化和执行构造代码块。

### 1.2 类加载的完整过程是怎样的？

类加载分为 **加载、连接（验证、准备、解析）、初始化、使用、卸载** 五个阶段。

| 阶段 | 说明 |
|------|------|
| 加载 | 通过类的全限定名获取二进制字节流，将静态存储结构转化为方法区的运行时数据结构，生成 `java.lang.Class` 对象 |
| 验证 | 校验字节流是否符合 JVM 规范，防止恶意代码 |
| 准备 | 为**类变量**（static）分配内存并设置初始值（如 int → 0，引用 → null）。`final static` 变量在此阶段直接赋用户定义的值 |
| 解析 | 将常量池中的符号引用替换为直接引用（内存地址或偏移量） |
| 初始化 | 执行 `<clinit>` 方法，合并所有静态变量赋值和静态代码块。父类的 `<clinit>` 先执行 |

> 注意：以下情况不会触发类的初始化：
> - 通过子类引用父类的静态字段（只触发父类初始化）
> - 定义对象数组
> - 常量在编译期已存入调用类的常量池
> - 通过 `Class.forName` 且 `initialize=false`
> - 通过 `ClassLoader.loadClass`

### 1.3 类加载器有哪些？什么是双亲委派模型？

- **启动类加载器**（Bootstrap）：加载 `JAVA_HOME/lib` 目录下的核心类库
- **扩展类加载器**（Extension）：加载 `JAVA_HOME/lib/ext` 下的类库
- **应用程序类加载器**（Application）：加载 classpath 上的用户类

**双亲委派模型**：当一个类加载器收到加载请求时，首先将请求委派给父加载器，依次向上，只有父加载器无法完成时才自己加载。这样做保证了核心类库的安全（如 `java.lang.Object` 总是由 Bootstrap 加载，不会被篡改）。

## 2. 线程实现

### 2.1 JVM 是如何实现线程的？

JVM 中的线程本质上是映射到底层操作系统的线程实现的。主流实现方式：

- **内核线程实现**：直接由操作系统内核支持，轻量级进程与内核线程 1:1 映射。Java 线程的创建、调度、同步都由内核完成，开销较大。
- **用户线程实现**：完全在用户态实现，内核感知不到，但实现复杂且容易阻塞。
- **混合实现**：用户线程 + 轻量级进程。

HotSpot JVM 在 Windows/Linux 上采用 **1:1 内核线程模型**，即一个 Java 线程对应一个操作系统线程。线程的创建、销毁、调度依赖于操作系统提供的 pthread 或 Windows API。

## 3. JVM 内存结构（运行时数据区）

| 区域 | 线程共享 | 主要作用 |
|------|----------|----------|
| 程序计数器 | 私有 | 记录当前线程执行的字节码行号 |
| Java 虚拟机栈 | 私有 | 每个方法执行时创建栈帧，存储局部变量表、操作数栈、动态链接、方法出口等 |
| 本地方法栈 | 私有 | 为 Native 方法服务（HotSpot 将虚拟机栈和本地方法栈合并） |
| Java 堆 | 共享 | 存放所有对象实例和数组，是 GC 的主要管理区域 |
| 方法区 | 共享 | 存储已加载的类信息、常量、静态变量、即时编译器编译后的代码等（JDK 8 以后用元空间 Metaspace 实现，使用本地内存） |
| 运行时常量池 | 共享 | 方法区的一部分，存放编译期生成的字面量和符号引用 |

> 补充：**直接内存（堆外内存）** 不属于运行时数据区，但被频繁使用（如 NIO 的 `ByteBuffer`），受 `-XX:MaxDirectMemorySize` 限制。

## 4. JVM 内存分区 vs Java 内存模型（JMM）

- **JVM 内存分区**：是 JVM 运行时数据区的物理划分，如堆、栈、方法区等，解决“数据存储在哪里”的问题。
- **Java 内存模型（JMM）**：是一种抽象规范，定义多线程共享变量的读写规则，解决可见性、有序性、原子性问题。它抽象出**主内存**和**工作内存**的概念，并提供 `volatile`、`synchronized` 等保证。

> 常见误区：不要将 JMM 和 JVM 内存分区混淆。

## 5. 垃圾判断机制

### 5.1 如何判断一个对象是否可以被回收？

- **引用计数法**：每个对象维护一个引用计数器，为 0 时回收。缺点是无法解决循环引用（如 A ↔ B）。
- **可达性分析算法**（Java 使用）：以一系列 **GC Roots** 为起点，向下搜索引用链，不可达的对象被判定为可回收。

**GC Roots** 包括：
- 虚拟机栈（栈帧中的本地变量表）中引用的对象
- 方法区中静态属性引用的对象
- 方法区中常量引用的对象
- Native 方法栈中 JNI 引用的对象
- 活跃线程对象等

### 5.2 什么是三色标记法？

三色标记是并发标记阶段的一种算法，将对象分为三种颜色：
- **白色**：尚未被访问的对象（初始状态），最终白色对象为不可达对象，可回收。
- **灰色**：自身已被访问，但其引用的对象尚未被全部扫描。
- **黑色**：自身及引用的对象都已扫描完成。

在并发标记过程中，可能会发生“浮动垃圾”或“对象丢失”问题，需要通过**读写屏障**解决。

## 6. 垃圾回收算法

| 算法 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| 标记-清除 | 标记不可达对象，然后清除 | 简单 | 内存碎片多，效率不高 | 老年代（配合CMS） |
| 复制 | 将内存一分为二，存活对象复制到另一半 | 无碎片，效率高 | 内存利用率低（≤50%） | 新生代（对象存活率低） |
| 标记-整理 | 标记后让存活对象向一端移动，再清理边界外内存 | 无碎片，空间利用率高 | 移动对象开销大 | 老年代 |

### 6.1 分代收集与 Appel 式回收

- **新生代**：使用复制算法。分为 Eden、From Survivor、To Survivor，默认比例 8:1:1。Minor GC 时，将 Eden 和 From 中存活的对象复制到 To，然后清空 Eden 和 From，最后交换 From 和 To。
- **老年代**：使用标记-清除或标记-整理算法（对象存活率高，大对象直接进入老年代）。

对象晋升规则：每经历一次 Minor GC 仍存活，年龄 +1，达到阈值（默认 15）则进入老年代。动态年龄判定也可能提前晋升。

## 7. 垃圾收集器（重点）

### 7.1 常见收集器对比

| 收集器 | 区域 | 算法 | 特点 |
|--------|------|------|------|
| Serial | 新生代 | 复制 | 单线程，Stop-The-World，简单高效 |
| ParNew | 新生代 | 复制 | Serial 的多线程版本 |
| Parallel Scavenge | 新生代 | 复制 | 吞吐量优先，可控制自适应调节 |
| Serial Old | 老年代 | 标记-整理 | 配合 Serial 使用 |
| Parallel Old | 老年代 | 标记-整理 | 吞吐量优先 |
| CMS | 老年代 | 标记-清除 | 并发收集，低停顿，产生碎片 |
| **G1** | 全堆 | 复制+标记-整理 | 分区（Region），可预测停顿时间 |

### 7.2 G1 收集器详解

G1（Garbage First）将堆划分为多个大小相等的 Region，每个 Region 逻辑上扮演 Eden、Survivor、Old 或 Humongous（巨型对象区）。

**G1 回收步骤**：
1. **初始标记**（STW）：标记 GC Roots 直接可达的对象。
2. **并发标记**：从 GC Roots 开始进行可达性分析，与用户线程并发。
3. **最终标记**（STW）：修正并发标记期间因用户程序导致变动的标记。
4. **筛选回收**（STW + 并发）：根据回收价值排序，选择部分 Region 进行垃圾回收，复制存活对象到空闲 Region。

G1 通过设置期望的停顿时间（`-XX:MaxGCPauseMillis`）来优先回收垃圾最多的 Region。

> 补充：JDK 9 之后，G1 成为默认垃圾收集器。

## 8. 四种引用类型

| 引用类型 | 回收时机 | 用途 |
|----------|----------|------|
| 强引用 | 永不回收 | 普通 `new` 对象 |
| 软引用 | 内存不足时回收 | 实现内存敏感缓存（`SoftReference`） |
| 弱引用 | 下一次 GC 时回收 | 弱缓存、WeakHashMap |
| 虚引用 | 任何时候都可能回收，无法通过它获取对象实例 | 对象回收跟踪（`PhantomReference`，必须配合引用队列） |

## 9. Minor GC 频繁的原因及调优参数

### 9.1 导致 Minor GC 频繁的常见原因

- 新生代空间太小，对象过早晋升或频繁填满 Eden
- 大对象直接进入老年代，但老年代空间也不足，触发 Full GC
- 内存分配速率过高（如大量临时对象）
- Survivor 空间过小，导致对象直接晋升到老年代

### 9.2 常用 JVM 参数

| 参数 | 作用 |
|------|------|
| `-Xms` | 堆初始大小 |
| `-Xmx` | 堆最大大小 |
| `-Xmn` | 新生代大小 |
| `-XX:SurvivorRatio` | Eden 与单个 Survivor 的比例，默认 8 |
| `-XX:NewRatio` | 老年代与新生代的比例 |
| `-XX:+PrintGCDetails` | 打印 GC 日志 |
| `-XX:MaxGCPauseMillis` | G1 期望的最大停顿时间 |
| `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize` | 元空间初始/最大大小 |

> 调优建议：先分析 GC 日志，判断是新生代太小还是对象分配过快，再相应调整 `-Xmn` 或 `-XX:SurvivorRatio`。

## 10. 补充：内存溢出与内存泄漏

- **内存溢出（OOM）**：JVM 内存不足，无法继续分配对象。常见场景：堆溢出、方法区溢出、直接内存溢出、栈溢出。
- **内存泄漏**：对象不再被使用但仍被引用（GC Roots 可达），导致无法回收。常见原因：静态集合类未清理、监听器未移除、连接未关闭等。

> 排查工具：jmap、jstat、MAT、VisualVM、Arthas。
