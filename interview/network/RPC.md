# RPC

### 简述rpc框架？实现机制、调用过程

几个关键问题

**Call ID映射**。我们怎么告诉远程机器我们要调用Multiply，而不是Add或者FooBar呢？在本地调用中，函数体是直接通过函数指针来指定的，我们调用Multiply，编译器就自动帮我们调用它相应的函数指针。但是在远程调用中，函数指针是不行的，因为两个进程的地址空间是完全不一样的。所以，在RPC中，所有的函数都必须有自己的一个ID。这个ID在所有进程中都是唯一确定的。客户端在做远程过程调用时，必须附上这个ID。然后我们还需要在客户端和服务端分别维护一个 {函数 <--> Call ID} 的对应表。两者的表不一定需要完全相同，但相同的函数对应的Call ID必须相同。当客户端需要进行远程调用时，它就查一下这个表，找出相应的Call ID，然后把它传给服务端，服务端也通过查表，来确定客户端需要调用的函数，然后执行相应函数的代码。

**序列化和反序列化**。客户端怎么把参数值传给远程的函数呢？在本地调用中，我们只需要把参数压到栈里，然后让函数自己去栈里读就行。但是在远程过程调用时，客户端跟服务端是不同的进程，不能通过内存来传递参数。甚至有时候客户端和服务端使用的都不是同一种语言（比如服务端用C++，客户端用Java或者Python）。这时候就需要客户端把参数先转成一个字节流，传给服务端后，再把字节流转成自己能读取的格式。这个过程叫序列化和反序列化。同理，从服务端返回的值也需要序列化反序列化的过程。

**网络传输**。远程调用往往用在网络上，客户端和服务端是通过网络连接的。所有的数据都需要通过网络传输，因此就需要有一个网络传输层。网络传输层需要把Call ID和序列化后的参数字节流传给服务端，然后再把序列化后的调用结果传回客户端。只要能完成这两者的，都可以作为传输层使用。因此，它所使用的协议其实是不限的，能完成传输就行。尽管大部分RPC框架都使用TCP协议，但其实UDP也可以，而gRPC干脆就用了HTTP2。Java的Netty也属于这层的东西

```
// Client端 
//    int l_times_r = Call(ServerAddr, Multiply, lvalue, rvalue)
1. 将这个调用映射为Call ID。这里假设用最简单的字符串当Call ID的方法
2. 将Call ID，lvalue和rvalue序列化。可以直接将它们的值以二进制形式打包
3. 把2中得到的数据包发送给ServerAddr，这需要使用网络传输层
4. 等待服务器返回结果
5. 如果服务器调用成功，那么就将结果反序列化，并赋给l_times_r

// Server端
1. 在本地维护一个Call ID到函数指针的映射call_id_map，可以用std::map<std::string, std::function<>>
2. 等待请求
3. 得到一个请求后，将其数据包反序列化，得到Call ID
4. 通过在call_id_map中查找，得到相应的函数指针
5. 将lvalue和rvalue反序列化后，在本地调用Multiply函数，得到结果
6. 将结果序列化后通过网络返回给Client
```

### 常见的RPC框架

**1. gRPC**
- Google开源的高性能RPC框架
- 使用Protocol Buffers作为接口定义语言和序列化格式
- 基于HTTP/2协议，支持多路复用
- 支持多种编程语言：Go、Java、Python、C++等
- 支持四种调用模式：一元调用、服务端流、客户端流、双向流

**2. Dubbo**
- 阿里巴巴开源的高性能Java RPC框架
- 支持多种协议：dubbo协议、RMI、Hessian、HTTP等
- 提供完善的服务治理功能：负载均衡、服务发现、容错机制等
- 与Spring生态集成良好

**3. Thrift**
- Facebook开源的跨语言服务开发框架
- 包含完整的RPC栈：接口定义语言(IDL)、序列化框架、RPC库
- 支持多种编程语言
- 相对轻量，性能较好

**4. Motan**
- 新浪微博开源的RPC框架
- 支持Spring集成
- 支持多种协议和注册中心

**5. Spring Cloud OpenFeign**
- 声明式的HTTP客户端
- 虽然不是传统意义上的RPC，但提供了类似RPC的调用体验
- 与Spring Cloud生态集成良好

### 为什么不直接使用HTTP请求，而用rpc框架

虽然HTTP也可以实现远程调用，但RPC框架相比直接使用HTTP有以下优势：

**1. 性能优势**
- **协议开销小**：RPC通常使用二进制协议，而HTTP/1.1是文本协议，解析成本更高
- **更高效的序列化**：RPC框架常使用Protobuf、Thrift等高效的二进制序列化，比HTTP常用的JSON序列化体积更小、速度更快
- **连接复用**：RPC框架支持长连接和连接池，避免频繁建立连接的开销

**2. 调用体验**
- **像本地调用一样**：RPC提供了类似本地函数调用的接口，编程体验更好，代码更简洁
- **强类型支持**：通过IDL（接口定义语言）定义服务接口，编译时类型检查，减少运行时错误

**3. 功能完整性**
- **内置服务治理**：RPC框架通常内置负载均衡、服务发现、熔断降级等功能
- **更好的错误处理**：有完善的异常处理和重试机制
- **超时控制**：支持调用超时设置和取消

**4. 场景差异**
- **HTTP适合**：服务对外暴露、跨语言调用、简单的CRUD操作
- **RPC适合**：内部微服务间通信、高性能要求场景、复杂业务逻辑

### gRPC使用的是什么通信协议？

HTTP/2

### gRPC为什么使用的是HTTP/2，而不是TCP或者UDP

gRPC选择HTTP/2作为底层传输协议是基于以下考虑：

**相比TCP：**
- HTTP/2在TCP之上提供了更丰富的特性，解决了传统HTTP/1.1的性能问题
- TCP是传输层协议，只提供可靠的字节流传输，而HTTP/2提供了应用层的多路复用、流控等高级特性
- 如果直接基于TCP，gRPC需要自己实现这些功能，增加了复杂度
- HTTP/2的二进制分帧层比纯文本的HTTP/1.1更高效，解析成本更低

**相比UDP：**
- RPC调用通常需要可靠的通信保证，UDP不保证可靠性，丢包会导致调用失败
- 虽然UDP有性能优势，但gRPC更关注调用的可靠性、一致性和易用性
- 对于某些对延迟极敏感的场景，gRPC也支持通过QUIC（基于UDP的协议）实现

**HTTP/2的核心优势：**

1. **多路复用（Multiplexing）**
   - 在一个TCP连接上可以并发发送多个请求和响应
   - 解决了HTTP/1.1的队头阻塞问题，提高连接利用率

2. **二进制协议**
   - 采用二进制格式而非文本，解析效率更高
   - 更紧凑的编码，减少带宽消耗

3. **头部压缩（HPACK）**
   - 使用HPACK算法压缩HTTP头部
   - 减少重复传输的开销，特别是在频繁调用时效果明显

4. **流控（Flow Control）**
   - 支持流级别的流控，可以精细控制数据传输速率
   - 避免慢消费者阻塞整个连接

5. **服务端推送**
   - 支持服务端主动推送数据
   - 配合gRPC的流式调用模式，实现双向流通信

6. **更好的网络兼容性**
   - HTTP/2更容易穿越防火墙和代理
   - 可以复用现有的HTTP基础设施

**总结**：gRPC选择HTTP/2是在性能、可靠性、易用性和兼容性之间的最佳平衡点。它既避免了直接使用TCP带来的开发复杂度，又避免了使用UDP的可靠性问题，同时获得了HTTP/2的多路复用等高性能特性。
