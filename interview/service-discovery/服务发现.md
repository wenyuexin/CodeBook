## 服务注册与发现基础

### 一、基础概念

#### 1\. 什么是服务注册与发现？为什么微服务架构中需要它？

**参考答案**：

服务注册与发现是微服务架构中的核心机制，用于解决动态、弹性、多实例环境下服务间的网络定位问题。

- **服务注册**：服务提供者启动时，将自己的网络地址（IP + 端口）、元数据（版本、权重等）注册到注册中心。

- **服务发现**：服务消费者从注册中心获取目标服务实例列表，并通过负载均衡选择一个实例发起调用。

**为什么需要**：

- 实例动态变化（弹性伸缩、故障重启、发布上线），固定 IP/端口不可行。

- 解耦服务提供者和消费者，消费者无需硬编码地址。

- 支持健康检查，自动剔除不健康实例。

- 实现蓝绿、金丝雀等高级发布策略。

---

#### 2\. 服务注册与发现的核心流程包含哪几个步骤？

**参考答案**：

1. **启动注册**：服务提供者启动后向注册中心发送注册请求（包含服务名、IP、端口、元数据）。

2. **健康检查**：注册中心定期检查已注册实例的健康状态（心跳、探测），剔除不健康的实例。

3. **获取实例**：消费者启动或定期拉取服务实例列表，并可选择缓存到本地。

4. **变更通知**：当实例列表变化（新增、删除、健康状态变更），注册中心主动推送或消费者轮询感知。

5. **负载均衡**：消费者根据本地策略（轮询、随机、权重等）选择一个实例调用。

---

#### 3\. 服务注册中心需要满足哪些关键特性？

**参考答案**：

- **高可用**：注册中心本身必须集群部署，避免单点故障。

- **一致性 vs 可用性**：根据场景在 CP 和 AP 之间权衡。

- **服务健康检查**：能自动剔除故障实例，防止消费者调用失败。

- **实时性**：服务变更能尽快被消费者感知（秒级或毫秒级）。

- **可扩展**：支持海量服务实例（数千至数万）。

- **多语言/多协议**：提供多种客户端 SDK 或 API。

- **元数据管理**：支持标签、权重、版本等路由信息。

### 二、常用中间件对比

#### 4\. 请对比 Nacos、Eureka、Consul、ZooKeeper 作为注册中心的异同。

**参考答案**：

|特性|Nacos|Eureka|Consul|ZooKeeper|
|-|-|-|-|-|
|**CAP 模型**|默认 AP（可切换 CP）|AP|CP|CP|
|**健康检查**|心跳 + 主动探测（TCP/HTTP/MySQL）|心跳（Renew）|多种（TCP/HTTP/gRPC/脚本）|心跳（Session 存活）|
|**服务实例管理**|支持权重、元数据、临时/持久实例|只支持简单元数据|支持健康状态、元数据|需自行设计|
|**配置中心**|内置，功能强大|无|内置（KV 存储）|可基于 ZNode 实现（非原生）|
|**多数据中心**|支持|不支持|支持（通过 WAN Gossip）|需人工同步|
|**控制台 UI**|功能丰富|有但简陋|完善，带 Web UI|无原生 UI（第三方工具）|
|**一致性协议**|Distro（AP）/ Raft（CP）|无（基于心跳、自我保）|Raft（CP）|ZAB（类似 Raft）|
|**语言/生态**|Java，Spring Cloud Alibaba|Java，Spring Cloud Netflix（已停更）|Go，Spring Cloud Consul|Java，Dubbo 早期方案|
|**淘汰趋势**|活跃，主流|已进入维护状态，不再开发新特性|活跃，部分企业使用|不适合纯服务发现（重量级，维护成本高）|

---

#### 5\. Eureka 的自我保护机制是什么？为什么需要它？

**参考答案**：

**自我保护机制**：当 Eureka Server 在短时间内（默认 15 分钟）收到的心跳续约比例低于阈值（85%），Server 会认为可能发生了网络故障，不再剔除任何服务实例，同时进入自我保护模式。

**为什么需要**：在分布式系统中，网络分区或短暂抖动可能导致大量服务实例未能及时发送心跳。如果此时直接剔除实例，反而会让消费者调用到实际上健康的服务（只是心跳未送达），造成大规模误判。自我保护机制优先保证可用性（AP），宁愿保留可能已死的实例，也不误杀健康实例。

**缺点**：在自我保护模式下，消费者可能拿到已下线的实例，需要配合客户端重试、熔断机制。

---

#### 6\. ZooKeeper 作为注册中心为什么不推荐？它的最大问题是什么？

**参考答案**：

ZooKeeper 基于 CP 模型，在发生网络分区或 Leader 选举时，会暂停服务注册与发现（不可用），直到选出新的 Leader。这对于服务发现来说，可能导致整个微服务调用链断裂。

**主要问题**：

- **没有内置健康检查**：依赖客户端主动发送心跳（Session 存活），如果客户端进程僵死但 TCP 连接仍在，ZooKeeper 无法剔除。

- **不适合大量临时节点**：每个服务实例注册为临时节点，当实例大规模重启时，ZooKeeper 会产生大量节点创建/删除事件，导致集群性能抖动（甚至雪崩）。

- **没有元数据管理**：无法存储权重、版本等路由信息。

- **无服务查询 UI**：需要第三方工具查看注册状态。

因此，ZooKeeper 更适合分布式协调（选主、分布式锁、配置存储），而不是纯服务注册发现。Dubbo 早期使用 ZK，现已推荐 Nacos。

---

#### 7\. Consul 与 Nacos 都支持服务发现和配置中心，请简要对比。

**参考答案**：

|维度|Consul|Nacos|
|-|-|-|
|开发语言|Go|Java|
|一致性协议|Raft（强一致 CP）|默认 AP（Distro），可切 CP（Raft）|
|健康检查|丰富（脚本、TCP、HTTP、gRPC）|心跳 + 主动探测（TCP/HTTP）|
|多数据中心|原生支持（WAN Gossip）|支持（需手动配置同步）|
|配置格式|KV 存储，支持多种格式（通过工具）|支持 YAML、Properties、JSON、TEXT 等|
|配置监听|阻塞查询（Long Polling）|长轮询 + gRPC 推送|
|生态集成|Spring Cloud Consul，K8s|Spring Cloud Alibaba，Dubbo，K8s|
|易用性|有 Web UI，学习曲线平缓|功能更丰富，控制台更强大|

**结论**：两者都是优秀选择，若技术栈以 Java 为主、倾向 AP 模式、需要强配置中心能力，选 Nacos；若需要多数据中心、强一致性（CP）、技术栈多语言，选 Consul。

---

#### 8\. 在微服务架构中，如何选择合适的注册中心？请给出决策因素。

**参考答案**：

决策因素包括：

1. **一致性需求**：需要强一致（CP）还是高可用（AP）？例如金融系统可能更倾向 CP，普通业务倾向 AP。

2. **配置中心需求**：是否需要一体化的配置管理？Nacos、Consul 内置；Eureka 无；ZK 需自己实现。

3. **技术栈与生态**：Java 为主且使用 Spring Cloud Alibaba → Nacos；Netflix 栈（已过时）→ Eureka；多语言或 K8s 环境 → Consul。

4. **运维复杂度**：ZK 运维成本高（需了解 ZAB 协议、磁盘管理）；Nacos、Consul 相对友好。

5. **性能与规模**：需要支持上万实例？Nacos 和 Consul 均能支持，ZK 在高频临时节点场景下性能较差。

6. **社区活跃度**：Eureka 已停止迭代，不推荐新项目使用；Nacos 和 Consul 活跃。

**推荐**：新项目首选 Nacos，其次 Consul；避免 Eureka 和 ZooKeeper 作为纯注册中心。

---

#### 9\. 什么是服务健康检查？注册中心如何实现健康检查？

**参考答案**：

服务健康检查是注册中心判断服务实例是否存活、能否正常处理请求的机制。

**实现方式**：

- **客户端心跳**：服务实例定期向注册中心发送心跳（如每 5 秒），注册中心若超过一定时间（如 15 秒）未收到，标记为不健康；超时更久则剔除。

- **注册中心主动探测**：注册中心主动向服务实例的指定端点（如 HTTP `/health`）发起请求，根据响应状态判断健康与否。

- **被动健康检查**：通过业务请求失败率、TCP 连接状态等间接判断（较少使用）。

**混合模式**：Nacos、Consul 支持心跳 + 主动探测，Eureka 只用心跳，ZK 依赖 Session 存活。

---

#### 10\. 服务消费者如何感知注册中心中服务实例的变化？请说明推和拉两种模式。

**参考答案**：

- **拉模式（Pull）**：消费者定期轮询注册中心，获取最新实例列表。优点是实现简单，缺点是延迟较高（取决于轮询间隔），且产生无效请求。

- **推模式（Push）**：注册中心在实例列表变化时主动通知所有订阅的消费者。优点是实时性好，缺点是注册中心需维护长连接或消息队列。

**实际混合**：大多数注册中心采用“长轮询”或“监听器”机制。例如 Nacos 使用 UDP 或 gRPC 流推送 + 客户端本地缓存；Eureka 使用拉模式（默认 30 秒增量拉取）；Consul 使用阻塞查询（相当于长轮询）。
