## ZooKeeper

### 1. ZooKeeper 是什么？它主要解决什么问题？

**参考答案**：

ZooKeeper 是一个开源的**分布式协调服务**，提供高可用、高性能、强一致性的数据管理能力。它基于 **ZAB（ZooKeeper Atomic Broadcast）协议** 实现数据一致性。

**主要解决问题**：
- **分布式协调**：选主、分布式锁、队列、屏障等。
- **配置管理**：存储动态配置，通过 watch 机制实时通知变更。
- **命名服务**：类似 DNS，通过路径定位资源。
- **服务注册与发现**：作为注册中心存储服务实例地址（早期 Dubbo 使用）。

---

### 2. ZooKeeper 的数据模型是怎样的？与文件系统有何异同？

**参考答案**：

ZooKeeper 的数据模型是**层次化的命名空间**，类似文件系统，但每个节点（ZNode）既可以存储数据，也可以有子节点。

**特点**：
- **ZNode**：每个节点有路径（如 `/app/service`），可存储少量数据（默认 ≤ 1MB）。
- **节点类型**：
  - **持久节点（Persistent）**：创建后一直存在，除非主动删除。
  - **临时节点（Ephemeral）**：与客户端会话绑定，会话结束则自动删除。
  - **有序节点（Sequential）**：创建时自动在路径后追加递增序号（如 `/lock-00000001`）。
- **版本号**：每个 ZNode 有三个版本（dataVersion、cversion、aclVersion），用于乐观锁。
- **watch 机制**：客户端可在 ZNode 上注册监听，当节点数据或子节点变化时收到通知。

**与文件系统的区别**：文件系统主要存储大文件数据，ZooKeeper 存储小数据块（元数据），且支持瞬时节点和 watch。

---

### 3. 请简述 ZAB 协议的核心工作机制。ZooKeeper 如何保证数据一致性？

**参考答案**：

ZAB（ZooKeeper Atomic Broadcast）是 ZooKeeper 保证分布式一致性的核心协议，包含两个阶段：**消息广播** 和 **崩溃恢复**。

**正常运行时（Leader 正常）**：
1. **Leader 广播**：Leader 接收客户端写请求，生成提案（Proposal）并分配 ZXID（ZooKeeper Transaction ID）。
2. **Follower 投票**：Follower 将提案写入本地日志，返回 ACK。
3. **提交**：Leader 收到超过半数 ACK 后，发送 commit 指令，所有节点应用该提案。

**Leader 故障时（崩溃恢复）**：
1. **选举新 Leader**：根据 ZXID 和 myid 选举出拥有最新数据的节点。
2. **同步数据**：新 Leader 确保半数以上节点与其数据一致，然后恢复广播模式。

**一致性保证**：
- **顺序一致性**：客户端请求按 ZXID 顺序执行。
- **原子性**：提案要么所有节点都提交，要么都不提交（通过半数 ACK）。
- **单一系统映像**：客户端无论连接哪个节点，看到的数据视图一致（最终）。

### 4. ZooKeeper 中的 ZXID 是什么？它在选举中的作用是什么？

**参考答案**：

**ZXID**（ZooKeeper Transaction ID）是一个 64 位整数，高 32 位代表 Leader 的 epoch（任期），低 32 位是当前任期内的事务序号。每次写提案会生成一个新的 ZXID，全局递增。

**在选举中的作用**：
- 选举时，节点之间比较 (ZXID, myid)。ZXID 大的节点代表数据更新，优先成为 Leader。
- 如果 ZXID 相同，则比较 myid（节点编号），大的胜出。
- 这样可以保证拥有最新数据的节点当选，避免数据丢失。

### 5. ZooKeeper 的 watch 机制是如何工作的？有哪些注意事项？

**参考答案**：

**工作原理**：
- 客户端在读取某个 ZNode 时可以设置 watch（通过 `getData`、`getChildren`、`exists`）。
- 当该 ZNode 的数据或子节点发生变化时，ZooKeeper 会触发 watch，向客户端发送一个事件通知（WatcherEvent）。
- 客户端收到通知后，可以再次读取最新数据。

**注意事项**：
- **一次性**：watch 只触发一次，如果需要持续监听，必须每次收到通知后重新设置 watch。
- **异步性**：通知是异步发送的，客户端可能在收到通知前已再次设置 watch，不会丢事件。
- **顺序保证**：客户端先看到变更，后收到 watch 事件（因为事件是在变更之后生成的）。
- **性能**：大量 watch 会影响服务端性能，不建议对每个节点都设置。

### 6. ZooKeeper 中临时节点（Ephemeral）的作用是什么？与持久节点的区别？

**参考答案**：

临时节点的生命周期与客户端会话绑定。当创建该节点的客户端会话结束（主动关闭或超时），临时节点会自动被删除。

**区别**：

| 特性 | 持久节点 | 临时节点 |
|------|----------|----------|
| 生命周期 | 直到主动删除 | 会话结束自动删除 |
| 子节点 | 可以创建子节点 | 不能有子节点（ZK 3.x 后允许？实际上临时节点仍不能有子节点） |
| 用途 | 存储持久化配置、服务元数据 | 服务注册（实例下线自动清除）、分布式锁（崩溃自动释放） |

**典型应用**：服务注册中心，每个服务实例注册为临时节点，宕机后自动从注册表移除。

### 7. 如何使用 ZooKeeper 实现分布式锁？请描述排他锁的实现思路。

**参考答案**：

**排他锁（互斥锁）实现**：
1. 在 ZooKeeper 上创建临时节点（如 `/lock`）。
2. 如果创建成功，则获得锁。
3. 如果节点已存在（锁被其他客户端持有），则在该节点上设置 watch，等待节点删除。
4. 当锁释放（节点删除）时，watch 触发，客户端再次尝试创建节点。

**问题**：惊群效应（所有等待的客户端同时竞争）。优化方案：使用有序临时节点实现公平锁。

**公平锁实现**：
- 每个客户端在锁目录下创建有序临时节点（如 `/lock/request-00000001`）。
- 获取锁目录下所有子节点，判断自己创建的节点是否为序号最小的。
- 如果是，获得锁；如果不是，监听前一个节点的删除事件。
- 前一个节点删除时，当前节点获得锁。

### 8. ZooKeeper 作为注册中心有什么缺点？为什么不推荐用于大规模微服务？

**参考答案**：

**缺点**：
1. **没有内置健康检查**：依赖客户端会话心跳，如果客户端进程僵死（但 TCP 连接未断），临时节点不会自动删除。
2. **不适合大量临时节点**：每个服务实例对应一个临时节点，当实例频繁上下线（如弹性伸缩），ZooKeeper 会产生大量事件和磁盘写入，导致性能下降（称为“惊群”或“写放大”）。
3. **没有元数据管理**：无法存储权重、版本、标签等路由信息，需额外存储。
4. **无服务查询 UI**：需要第三方工具查看注册状态。
5. **配置中心能力弱**：虽然可以存储配置，但没有版本管理、灰度发布、长轮询等高级特性。

**推荐场景**：分布式协调（选主、锁）、小规模服务发现（几十到几百实例）。大规模微服务推荐 Nacos 或 Consul。

### 9. ZooKeeper 集群需要至少几个节点？为什么是奇数个？

**参考答案**：

ZooKeeper 集群通常使用 **奇数个节点**，如 3、5、7。原因：
- **容错性**：集群可容忍 (N-1)/2 个节点故障。3 节点可容忍 1 台故障，4 节点也只能容忍 1 台（因为需要过半存活，4 台过半是 3 台），所以 4 节点并不比 3 节点有更好的容错性，反而浪费资源。
- **避免脑裂**：奇数个节点在选举时更容易形成多数派，避免平局（如 2 节点各得 1 票，无法选出 Leader）。

**最小节点数**：生产环境至少 3 节点。

### 10. ZooKeeper 的 Leader 选举过程是怎样的？请简述 FastLeaderElection 算法。

**参考答案**：

ZooKeeper 默认使用 **FastLeaderElection** 算法，基于 TCP 进行投票。

**选举触发**：Leader 宕机、半数以上 Follower 与 Leader 失联、集群启动时。

**过程**：
1. 每个节点投票给自己（投票包含 (ZXID, myid)），并将投票发送给其他节点。
2. 收到其他节点的投票后，比较 (ZXID, myid)：
   - 若收到的投票 ZXID 更大，或 ZXID 相同但 myid 更大，则更新自己的投票并重新广播。
   - 否则，忽略。
3. 当一个节点获得 **超过半数** 的相同投票，该节点成为 Leader。
4. Leader 开始同步数据，其他节点成为 Follower。

**特点**：投票轮数收敛快，通常几轮内就能选出 Leader。

### 11. ZooKeeper 的会话（Session）超时是如何管理的？超时后临时节点何时删除？

**参考答案**：

- 客户端创建会话时指定超时时间（如 10 秒）。服务器端可设置最小和最大超时限制（通常 2 倍 tickTime ~ 20 倍 tickTime）。
- 客户端定期发送心跳（PING）维持会话。服务器收到心跳则重置会话超时计时器。
- 若服务器在会话超时时间内未收到任何心跳，则判定会话过期，删除该会话创建的所有临时节点。
- **删除时机**：会话过期后，ZooKeeper 会立即删除临时节点，并通知其他客户端（watch 触发）。

**注意**：网络延迟可能导致客户端实际未超时但服务器认为超时，建议合理设置超时时间（如 10~30 秒）。

### 12. 如何保证 ZooKeeper 中存储的数据不会丢失？持久化机制是怎样的？

**参考答案**：

ZooKeeper 采用 **事务日志（Transaction Log） + 快照（Snapshot）** 进行持久化。

- **事务日志**：每次写操作都会追加到磁盘上的日志文件（`log.xxxx`），保证崩溃后可重放恢复。
- **快照**：定期（默认每 1000 次事务或一定时间间隔）将内存中的数据全量写入快照文件（`snapshot.xxxx`）。
- **恢复**：启动时先加载最新的快照，再重放其后的事务日志，恢复到崩溃前状态。

**防止丢失**：写操作必须刷盘（可通过 `fsync` 配置），但为了性能，可调整为不强制刷盘（可能丢失少数事务）。

### 13. ZooKeeper 在 Kafka 早期版本中扮演什么角色？为什么 Kafka 要移除对 ZooKeeper 的依赖？

**参考答案**：

**早期角色**：Kafka 使用 ZooKeeper 存储 broker 元数据、topic 配置、consumer group offset（旧版）和进行 Leader 选举（controller 选举）。

**移除原因**：
- **性能瓶颈**：ZooKeeper 不适合高吞吐的元数据读写，尤其是大规模 topic/partition。
- **运维复杂**：两个独立集群（Kafka + ZooKeeper）增加运维成本。
- **单点风险**：虽然 ZooKeeper 是高可用的，但 Kafka 对 ZK 的强依赖导致 ZK 抖动会影响整个 Kafka 集群。
- **新架构**：Kafka 2.8+ 引入基于 Raft 的 KRaft 模式，完全替代 ZooKeeper，简化部署。

### 14. 在 Java 中使用 ZooKeeper 原生 API 有哪些常见问题？有没有推荐的客户端？

**参考答案**：

**常见问题**：
- 需要手动处理连接建立和会话管理（重连、会话过期）。
- watch 是一次性的，需要手动重新注册。
- 异步回调模型较复杂。
- 无自动重试，需要自己实现。

**推荐客户端**：
- **Curator**（Netflix 开源）：封装了连接管理、重试、监听器保持、分布式锁等高级功能，是目前最流行的 ZooKeeper Java 客户端。
- **zkclient**（较老，不推荐）。

**Curator 示例**：
```java
CuratorFramework client = CuratorFrameworkFactory.newClient("zk:2181", new RetryNTimes(3, 1000));
client.start();
client.create().creatingParentsIfNeeded().forPath("/path", data);
client.getData().usingWatcher((CuratorWatcher) event -> {}).forPath("/path");
```

### 15. ZooKeeper 与 etcd 的主要区别是什么？你会如何选择？

**参考答案**：

| 维度 | ZooKeeper | etcd |
|------|-----------|------|
| **一致性协议** | ZAB | Raft（更简洁） |
| **API** | 基于 Jute 定制协议，需客户端 | gRPC + HTTP，跨语言友好 |
| **watch** | 一次性触发 | 长连接持续推送（可带历史版本） |
| **存储限制** | 默认 ≤ 1MB/节点 | 默认 2GB 总量，单个 key 不限（但建议小） |
| **运维** | 复杂，需熟悉四字母命令 | 简单，Prometheus 集成，etcdctl 友好 |
| **社区活跃度** | 较低（主要用于 Hadoop、Kafka 旧版） | 高（K8s 生态） |
| **典型用户** | 老系统、分布式协调需求 | 云原生、K8s、新项目 |

**选择建议**：
- 新项目且不需要与老系统兼容，优先 **etcd**。
- 已深度使用 ZooKeeper 且稳定运行，可继续保留。
- 需要强一致性和 watch，两者都可，但 etcd 开发体验更好。
